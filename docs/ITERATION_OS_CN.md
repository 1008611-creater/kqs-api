# 矿泉水API迭代操作系统

这份文档是项目的"活地图"。目标不是写漂亮口号，而是让每次迭代都知道自己在改哪条链路、用什么证据收口、什么时候该停手。

## 一、项目地图

### 1. 账号链路

用户从注册、登录、邮箱验证进入后台。关键页面是 `/login`、`/register`、`/dashboard`。这里的首要目标是让新同学知道自己下一步要做什么，而不是先理解整个系统。

### 2. 卡密链路

站外使用链动小铺售卖卡密，站内使用 `/redeem` 兑换。当前套餐链接集中维护在 `frontend/src/constants/onboarding.ts`，不要散落写进多个组件。兑换成功后必须把用户带到"创建 Key"。

### 3. 余额链路

余额是用户能否调用 API 的第一道门。余额不足时，提示必须包含下一步动作：购买卡密、兑换余额、再重试。第一阶段不重做支付系统，不接微信支付。

### 4. Key 链路

用户在 `/keys` 创建 Key。Codex 用户默认应该进入 `codex` 分组。未分组 Key 要明确提示"点击分组列选择 codex"，避免用户拿到 Key 却跑不通。

### 5. Codex 配置链路

正式入口是 `https://api.cauai.fun`，模型默认是 `gpt-5.5`，Responses 路径由 Codex 客户端自己拼。页面只长期展示脱敏 Key，完整 Key 只在刚创建或用户主动复制时出现。

### 6. 部署与缓存链路

线上入口走 Cloudflare。前端视觉或静态资源更新后，需要确认构建产物、服务状态、Cloudflare 缓存是否一致。涉及线上变更时，先记录可回滚点，再验证公网页面。

## 二、状态化新手闭环

新手进度只记录四个节点，不记录敏感内容：

- `purchase`：购买卡密
- `redeem`：兑换余额
- `key`：创建 Codex Key
- `config`：复制 Codex 配置

状态持久化在用户自定义属性 `sub2api_onboarding_state` 中。前端用 Pinia 做本地缓存，后端状态作为权威来源。刷新页面、换设备或重新登录后，仍然能继续显示下一步。

## 三、自动化节奏

### 半小时巡检

只读，不改代码。每次巡检要做：

- 读取记忆层：open work / blockers / 最近变更
- 查看 `git status --short`
- 检查是否有未完成验证或失败构建
- 输出 3 行以内状态：当前风险、下一步最小动作、是否需要人工介入

### 每小时小步推进

每次只做一个小而完整的改动。必须先看记忆层和 git 状态，再选择任务。完成后至少给出：

- 改了哪些文件
- 跑了哪些验证
- 是否需要部署
- 下一个最值钱的小任务

### 每周路线校准

每周复盘自动化产出、失败点和用户卡点。下一周只保留 1-3 个最高价值目标，避免项目被"看起来都重要"的小事拖散。

## 四、发布闸门

任何准备上线的迭代都要过这几项：

- 不覆盖用户或其他线程留下的未提交修改
- 发布镜像必须固定 tag，不把 `latest` 当成正式发布依据
- 发布前最近一次成功备份必须小于 30 小时
- 后端改动跑对应 Go 测试
- 前端改动跑 `pnpm run typecheck` 和 `pnpm run build`
- 涉及页面体验时做一次浏览器烟测
- 涉及线上时确认回滚方式和公网入口

## 五、下一轮优先级

1. 新手闭环指标：注册、兑换、创建 Key、首次成功请求
2. 错误恢复卡片：把常见错误直接转成可点击动作
3. 管理员运营面板：看新用户卡在哪一步，但不展示请求内容或密钥
